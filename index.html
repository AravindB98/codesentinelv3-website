What it is

Scan. Prove. Measure.

One product with three jobs: find the flaw, keep a checkable record of what found it, and measure whether the AI doing the finding is worth its cost.

01 · Scan

Two engines

  • 32 offline rules across Python, JavaScript, TypeScript, Java, Go, Ruby and PHP
  • An AI pipeline: a Sentinel that must cite evidence, a Quality Auditor, and an Evaluator that can reject findings
  • Text, JSON, SARIF, Markdown and HTML reports; CI gating; REST service; Docker and Helm
02 · Prove

Provenance

  • Every model response recorded once and never requested again
  • A hash-chained statement per result: code, model calls, prompts, retrieval, review trail, findings, code version
  • verify checks the chain, the records, a full replay and the evidence, with no model calls
03 · Measure

Evaluation and routing

  • Six configurations of one model, compared with paired statistics and intervals
  • Hosted models or your own open-weight model, including on an HPC cluster
  • A router that learns when a cheaper configuration is enough, scored on recorded runs

How it works

From source code to a finding you can check

The AI pipeline grounds each claim in a knowledge base, has a second agent challenge it, then leaves a record anyone can replay.

InputSource code
RetrieveOWASP and CWE passages
SentinelFinds flaws, must cite a passage
AuditorMaintainability findings
EvaluatorChecks citation, evidence, fix
ReportApproved findings only

↺ A rejected finding goes back to the Sentinel with feedback, for at most three rounds.

RecordEach model response stored once, keyed by hash
AttestA chained statement per result
VerifyChain, records, replay, evidence
MeasurePaired comparison across six configurations

1. Which mode do I need?

You want to Use Needs
Scan code with no network, no cost, same result every time Offline rule engine: codesentinel scan PATH --mock Python only
Scan code with AI reasoning beyond fixed patterns AI pipeline: codesentinel scan PATH An Anthropic API key
Keep scanned code inside your own network but still use AI The rig with your own model server: --backend openai --base-url ... A GPU machine serving an open-weight model
Check that a result was not edited and can be reproduced python -m codesentinel.rig verify The run folder and its dataset
Measure whether the AI pipeline is worth its cost on your code python -m codesentinel.rig run and analyze A labelled dataset

One caution before you start: the AI pipeline has only been measured in a small pilot. Treat its output as a reviewer's suggestions, not as a verdict. See the README section "What is proven and what is not".

3. Your first scan

Create a file with three obvious flaws:

# demo.py
import os, pickle, sqlite3
def f(cur, x):
    cur.execute(f"select * from t where id={x}")
    os.system("ls " + x)
    return pickle.loads(x)

Scan it offline:

codesentinel scan demo.py --mock

You should see three findings: SQL injection (CWE-89), insecure deserialization (CWE-502) and command injection (CWE-78), followed by a summary line.

Scan a whole project:

codesentinel scan ./my-project --mock

The exit code is 0 unless you ask for a gate with --fail-on.

4. Reading a finding

CRITICAL CWE-89     demo.py:3
  SQL Injection: CWE-89 (A03:2025 Injection)
  > cur.execute(f"select * from t where id={x}")
  fix: Use parameterized queries with placeholders instead of f-strings.
  provenance: patterns.md::PY-01 | confidence 0.94
Part Meaning
CRITICAL Severity: CRITICAL, HIGH, MEDIUM, LOW or INFO
CWE-89 The weakness class in the Common Weakness Enumeration
demo.py:3 File and line
A03:2025 Injection OWASP Top 10 2025 category
> line The code that triggered the finding
fix A concrete remediation
provenance The knowledge base passage that grounds the claim (document::passage id)
confidence 0 to 1. For rules it is a fixed value per rule; for AI review it is the model's own estimate and is not calibrated

A finding is a claim to check, not a fact. Open the file, read the line, and decide.

7. Using it in CI

The exit code does the gating. This fails the job when any finding is HIGH or CRITICAL:

codesentinel scan . --mock --fail-on HIGH -f sarif -o results.sarif

GitHub Actions:

name: CodeSentinel
on: [pull_request]
jobs:
  scan:
    runs-on: ubuntu-latest
    permissions:
      security-events: write
      contents: read
    steps:
      - uses: actions/checkout@v4
      - uses: AravindB98/CodeSentinel-v3@main
        with:
          path: .
          fail-on: HIGH
          offline: "true"            # rule engine only; remove and add anthropic-api-key for AI review

A complete workflow is in examples/github-code-scanning.yml. On GitLab, Azure DevOps or Jenkins, run the CLI and publish the SARIF file as an artifact.

Recommendation: gate builds on the offline rule engine, which gives the same answer every run. Use AI review as an advisory step until it has been evaluated on your own code.

8. Adopting on an existing codebase

A first scan of an old project can return hundreds of findings. Record them once, then fail only on new ones:

codesentinel baseline . -o .codesentinel-baseline.json
git add .codesentinel-baseline.json
codesentinel scan . --baseline .codesentinel-baseline.json --fail-on HIGH

Baselines store fingerprints that do not depend on line numbers, so moving code does not bring old findings back. Work the baseline down over time; it is a list of known debt, not an approval.

9. Configuration file

Put .codesentinel.yml in the project root. Flags override environment variables, which override this file.

include: ["**/*"]
exclude: ["**/vendor/**", "**/node_modules/**", "**/*.min.js"]
max_file_bytes: 1000000
concurrency: 8
quality: true                 # include maintainability findings
min_confidence: 0.5           # drop findings below this confidence
engine: auto                  # auto | deterministic | llm
baseline: .codesentinel-baseline.json
disabled_rules: ["CS-PY-WEAKHASH"]   # a rule id, a CWE, or a category
gate:
  severity_threshold: INFO
  fail_on: HIGH
llm:
  model: claude-sonnet-5-5
  retrieval_k: 6
  max_retries: 3

Environment variables are listed in ADMIN.md.

11. Verifying where a result came from

Use this when someone hands you a set of AI findings and you need to know they are the unedited output of a specific model and code version.

Try it offline in two minutes:

python -m codesentinel.rig run --dataset eval/datasets/paired_suite.json --out runs/demo --backend mock
python -m codesentinel.rig attest runs/demo
python -m codesentinel.rig verify runs/demo --dataset eval/datasets/paired_suite.json

Expected: "verified": true, 120 statements, an empty failures list. (This demo uses the built-in offline mock, so it shows the mechanism, not model quality.)

What you receive from a run's author

File in the run folder Contents
per_sample_*.jsonl One line per configuration, sample and replicate: findings, scores, cost
records_*.jsonl Every model request and response, stored once
attestations.jsonl One provenance statement per result, chained by hash
attestation_head.json The final hash, which identifies the whole run

How to check it

  1. Get the head hash from a place the author cannot change afterwards: a signed commit, a release note, a paper.
  2. Compare it with attestation_head.json.
  3. Run verify with the same dataset. Exit code 0 means every check passed.

Reading a failure

check What went wrong
chain A statement was altered, removed or reordered, or the head hash does not match
records A model response is missing or its content no longer matches its recorded hash
replay Re-running on recorded responses gives different findings, or needs a model call that was never recorded
evidence A finding points at lines that do not exist in the code
subject The scanned code is missing from the dataset or has changed

code_matches_attested_version: false is a warning, not a failure: the code you are verifying with differs from the version that produced the run. A passing replay under a different version is still informative, but note it.

What a pass means. The findings are the reproducible output of the recorded model responses under the stated configuration, and nothing was edited after attestation. It does not mean the findings are correct.

12. Running an evaluation

You need a dataset: a JSON Lines file where each line has sample_id, language, code and ground_truth (a list of {cwe_id, line_start, line_end}, empty for flaw-free samples). Section 13 shows how to build one.

Hosted model

export ANTHROPIC_API_KEY=sk-ant-...
python -m codesentinel.rig run --dataset study/data/dataset.jsonl \
       --out study/results/run-001 --backend anthropic --model <model id> --replicates 3

Your own model server (anything with an OpenAI-compatible endpoint, such as vLLM)

python -m codesentinel.rig run --dataset study/data/dataset.jsonl \
       --out study/results/run-002 --backend openai \
       --model <model name> --base-url http://HOST:8000/v1 --replicates 5 --seed 1000

Then

python -m codesentinel.rig analyze study/results/run-001
python -m codesentinel.rig attest  study/results/run-001
python -m codesentinel.rig verify  study/results/run-001 --dataset study/data/dataset.jsonl

Useful run options:

Option Meaning
--arms a b c Run only some configurations. equal_call needs full in the same run
--replicates N Repeat the whole run N times to measure run-to-run spread
--seed S Base seed; replicate k uses S + k (honoured by servers that accept a seed)
--limit N First N samples only, for a smoke test
--shard i/n Process shard i of n, for cluster job arrays

A run can be stopped and restarted. It skips what is already done and never requests a recorded response twice, so you are not charged again.

Reading analyze output

Field Meaning
recall_per_flaw Share of labelled flaws found
detected_all Share of flawed samples where every flaw was found
false_alarm_rate Share of flaw-free samples that got at least one finding
false_discovery_rate Share of all findings that matched no labelled flaw
silent_samples Samples with no findings at all. A sudden jump signals a broken run
primary_fp_difference_b_minus_a Mean per-sample difference in false positives, with a 95% bootstrap interval
recall_guardrail_0.05_met Whether recall dropped by no more than 0.05
tokens_per_true_finding Cost of one correct finding

Every proportion carries a 95% interval. With a small dataset the intervals are wide; report them as they are.

Running on a university or company cluster: study/hpc/README.md.

13. Labelling samples

make label REVIEWER=yourname          # opens http://127.0.0.1:8765

The tool shows one candidate at a time: the code with line numbers, the lines the fix changed (highlighted), a link to the fix commit and the advisory. Choose one decision:

Decision When
Flaw is real, of this class, and visible in this snippet You can point to the flaw in the code shown. Enter the lines
Flaw is real but cannot be judged from this snippet alone The fix depends on code outside the function
No flaw of any class in this snippet Use for the after-fix twin when the fix is complete here
Not this flaw, but another real flaw is present Describe it in the notes
Unsure It will be excluded and logged

Rules for honest labels: - Open the fix commit. The highlighted lines are a hint, not a label. - Label before any model has been run on the dataset. - Have a second person label a subset independently, with their own reviewer name.

Decisions are appended to study/data/labels/labels.jsonl with your name and the time. Build the dataset and measure agreement:

python -m codesentinel.rig build-dataset --primary yourname --second colleague --pairs-only

This writes study/data/dataset.jsonl and an inclusion log listing every excluded candidate and why.

15. Frequently asked questions

Does my code leave my machine? Not with the rule engine. With AI review it goes to the model provider, unless you serve an open-weight model yourself and use --backend openai.

Can I trust the AI pipeline's findings? Treat them as suggestions from a reviewer who is sometimes wrong. The pilot evidence is small. The rig exists so you can measure it on your own code.

Does a verified result mean the finding is real? No. Verification shows the finding is the unedited, reproducible output of a named model and code version. Whether it is true is a separate question answered by labelled evaluation.

Why did two AI scans of the same file differ? Hosted models are not perfectly repeatable even at temperature 0. The rig's --replicates option measures this spread.

How much does an AI evaluation cost? The full pipeline makes about three to six model calls per sample, and the six configurations together make roughly fifteen. Run with --limit 5 first and read tokens_per_sample in analyze.

Which languages are supported? The rule engine covers Python, JavaScript, TypeScript, Java, Go, Ruby and PHP. The AI pipeline accepts any of them but has been benchmarked only on Python.

Is it a replacement for Semgrep, CodeQL or Snyk? No. Those have far larger rule sets and data-flow analysis. Use CodeSentinel alongside them, or use its rig to evaluate an AI reviewer you are considering.

1. System overview

Layer Package Depends on Third-party requirements
Scanner codesentinel.engine, .rules, .graph, .rag, .reporters, .api nothing above it pydantic, PyYAML, NumPy; optional Anthropic SDK, LangGraph, ChromaDB, FastAPI
Rig codesentinel.rig Scanner standard library only
Provenance codesentinel.provenance Rig standard library only
Router codesentinel.router Rig, codesentinel.rl.bandit standard library only

Design rules that hold across v3:

  • The scanner source is not edited by the research layers. Ablations are applied from outside, as patches that are undone after each call.
  • A model is called at most once per distinct request. Everything after that is replay.
  • The sample is the unit of analysis. Findings are deduplicated before counting.
  • Mock output is never evidence. The offline mock exists to test plumbing.

Entry points: codesentinel (scanner CLI, codesentinel/cli.py) and python -m codesentinel.rig (codesentinel/rig/cli.py).

2. Scanner

2.1 Engine

codesentinel/engine.py discovers files (include and exclude globs, size cap), detects language per file, and routes each file to one of two backends:

  • _scan_one_deterministic: calls rules.detect(code, language).
  • _scan_one: runs the agent graph.

Results from either are projected onto one Finding model (codesentinel/models.py), deduplicated by fingerprint, filtered by baseline and policy (min_confidence, severity threshold), and handed to a reporter.

2.2 Rule engine

codesentinel/rules.py holds a list of Rule dataclasses:

Field Meaning
rule_id For example CS-PY-SQLI-FSTRING
language One of python, javascript, typescript, java, go, ruby, php. JavaScript rules also apply to TypeScript
cwe, owasp, category, severity, confidence, title, fix Reported as is
pattern A regular expression matched per line, case-insensitive
requires Optional substring that must appear somewhere in the file
rag_doc, rag_pid The knowledge base passage the rule cites

detect walks the lines once. For each line it takes the first applicable rule that matches and moves to the next line, so a line yields at most one finding. There is no data-flow analysis.

2.3 Agent graph

codesentinel/graph/build_graph.py builds a LangGraph StateGraph over CodeSentinelState (a TypedDict in graph/state.py), or a hand-written runner with the same routing when LangGraph is not installed.

security_sentinel -> code_quality_auditor -> evaluator -> (approved) assemble_report
                           ^                                   |
                           +------- (rejected, < 3 rounds) ----+
  • Security Sentinel (graph/agents/security_sentinel.py): builds a retrieval query from the language, a keyword list and the first 800 characters; retrieves 6 passages; calls the model with prompts/security.md; parses findings into SecurityFinding objects, dropping any that fail validation.
  • Code Quality Auditor: maintainability findings, never scored by the rig.
  • Evaluator Guardian (graph/agents/evaluator_guardian.py): first a programmatic check (citation present and in the retrieved set, fix at least 20 characters, confidence at least 0.5), then a model review with prompts/evaluator.md that can override the programmatic notes. A rejection writes feedback into the state and routes back to the Sentinel.
  • Circuit breaker: after 3 Sentinel rounds the graph terminates.

Two behaviours to know when reading results:

  1. When the breaker fires, assemble_report shows all Sentinel findings to the user, but the rig counts only Evaluator-approved findings, as the April harness did.
  2. A model or parse error in an agent is caught and becomes "no findings" with state["error"] set. The rig records error per row so a silent failure is visible.

2.4 Retrieval

codesentinel/rag/retriever.py tries three backends in order: ChromaDB (rag/chroma_store), a pickled scikit-learn TF-IDF index (rag/tfidf_index.pkl), then a pure-Python TF-IDF index. The corpus is three files in rag/data/: owasp_top10_2025.txt, cwe_subset.csv, patterns.md.

The backend in use changes what the Sentinel sees. The rig records it per result (retrieval.backend), and the provenance layer hashes the corpus and prompts into code_version.prompts_and_corpus_sha256. A stale pickled index was one cause of the empty runs of April 2026.

2.5 Model client

codesentinel/utils/llm_client.py exposes a module-level singleton through get_llm() with one method, complete(system, user, max_tokens, temperature) -> str, and a mode attribute ("real" or "mock"). The rig substitutes its own client by assigning llm_client._client.

2.6 Service, audit, licensing

codesentinel/api is a FastAPI app with API-key authentication (tenant:secret), tenant-scoped scan storage, rate limiting and Prometheus metrics. codesentinel/audit.py writes a hash-chained audit log of API activity. codesentinel/editions.py verifies Ed25519-signed licence tokens offline. These are documented in API.md, ADMIN.md and DEPLOYMENT.md. Note that the audit log (who called the service) and v3 provenance (what produced a finding) are separate chains.

3. Record-once model access

codesentinel/rig/record.py.

3.1 Request key

key = sha256( json([model, sha256(system_prompt), user_prompt,
                    max_tokens, temperature, seed, replicate]) )

Compact separators, ensure_ascii=False. The system prompt enters by hash so a stored record can be re-hashed without shipping the prompt text. replicate is part of the key, so replicate 1 is a new request even at temperature 0.

3.2 Store

RecordStore is an append-only JSON Lines file. put refuses to overwrite an existing key. Each record holds the request fields, the response, response_sha256, token usage, the served model string, latency and a UTC timestamp. record_is_intact(rec) recomputes both hashes.

3.3 Clients

Class Backend flag Talks to
AnthropicInner anthropic Anthropic Messages API
OpenAICompatInner openai Any OpenAI-compatible /chat/completions endpoint, through urllib; sends seed when given
CodeSentinelMockInner mock The scanner's offline mock
none replay Nothing; a missing record raises

RecordingClient wraps one of these and presents the scanner's client interface. It returns the stored response when the key exists and calls the inner client otherwise.

3.4 ReplayMiss

In replay-only mode an unrecorded request raises ReplayMiss, which derives from BaseException. This is deliberate. The agents catch Exception and convert failures to "no findings"; if ReplayMiss were an Exception, a missing recording would silently become a clean result.

4. Configurations and ablation switches

codesentinel/rig/arms.py.

Name Implementation
single_prompt One call with GENERIC_PROMPT, the April baseline prompt copied verbatim
equal_call single_prompt, then n - 1 rounds with REVIEW_PROMPT, where n is the number of calls full made on the same sample and replicate. No roles, no retrieval
full build_graph().invoke(state), findings filtered to Evaluator-approved ids
no_evaluator run_security_sentinel(state) only
no_grounding full with security_sentinel.get_retriever replaced by a stub returning no passages
no_specialisation full with security_sentinel._load_system_prompt returning GENERIC_PROMPT

_patched(client, ablation) is a context manager that swaps the client and applies one switch, then restores all three patched names in a finally block.

Limits to state when reporting:

  • no_grounding leaves the Evaluator's citation rules on. It measures grounding removed with the citation policy intact.
  • no_specialisation changes only the Sentinel's prompt. The Evaluator keeps its own.
  • equal_call matches call count, not token count.

The runner orders configurations so full runs before equal_call within each sample.

5. Scoring

codesentinel/rig/scoring.py.

Matching. A prediction matches a ground-truth flaw when the CWE ids are equal and the line ranges overlap within TOLERANCE = 2 lines. Each flaw is matched at most once.

Deduplication (new runs only). Predictions with the same CWE whose line ranges overlap or touch are merged before matching.

Sample-level outcomes.

Field Definition
is_positive The sample has at least one labelled flaw
tp, fn Labelled flaws found and missed
fp Deduplicated findings matching no labelled flaw
detected_all Positive sample with fn == 0
alarmed At least one finding
false_alarm Flaw-free sample with at least one finding

score_legacy reproduces the April rule exactly (no deduplication) and is used only by replay.

Known weakness. fp on a positive sample counts any finding beyond the labelled flaws as false, even if it is a real second flaw. The pre-registration draft proposes hand adjudication of those findings, or restricting the primary outcome to flaw-free samples.

Metric names are used strictly: false discovery rate is FP / (FP + TP); false-alarm rate is the share of flaw-free samples with a finding. The April files label the former "FPR".

8. Router

codesentinel/router/offline.py reuses codesentinel.rl.bandit.UCB1Bandit unchanged: one independent UCB-1 bandit per context bucket, exploration constant annealed from 1.414 toward 0.1.

  • Context: complexity_bucket(code) (short, medium, long by character count) and whether any of a fixed list of sink keywords appears. Both are available before any model call.
  • Arms: by default single_prompt, no_evaluator, full.
  • Utility: correct - cost_weight * tokens / max tokens on that sample, with cost_weight = 0.2; correct is 1 when a flawed sample is caught in full or a flaw-free sample raises no alarm.
  • Protocol: 200 random half splits. The bandit learns online on one half with utilities rescaled to [0, 1], then its greedy choice per context is scored on the other half. Contexts unseen in training fall back to the best fixed arm on the training half.
  • Comparators: always one arm, uniform choice, per-sample oracle.

Because every arm is observed on every sample, no off-policy estimator is needed.

Router lab (codesentinel/router/lab): a separate sandbox with a four-arm contextual bandit, a REINFORCE policy-gradient agent (PyTorch), a feature extractor, simulated agents, a simulation environment and a live orchestrator with a rule-based mode. It is research code excluded from linting, installed with the router-lab extra. Its recorded simulation results (study/router_sim/results) show the bandit at 0.4654 mean reward against 0.4604 for a uniform policy with overlapping 95% intervals, which is why routing is judged on recorded real runs instead. The policy-gradient agent and simulator were not re-run after being moved into the package. The output is marked "status": "exploratory". Wiring the router into the live scan path is not done.

9. Dataset pipeline

  1. Index (study/data/candidates/advisories_index.json): GitHub-reviewed advisories from 2025 and 2026 for PyPI packages that name exactly one CWE in the target classes and exactly one fix commit.
  2. Candidates (codesentinel/rig/candidates.py): for each advisory, git fetch --depth 2 the fix commit, find the changed non-test Python functions with ast, take the one with the most changed lines (at most 120 lines), and emit a pair: the function before the fix and after it, each prefixed by the file's import statements. Pairs where the fix touched other code are flagged fix_touches_other_code. Every skipped advisory is logged with its reason in build_log.json.
  3. Labels (codesentinel/rig/label_app.py): a local HTTP server on 127.0.0.1 that appends decisions to JSON Lines with reviewer and time.
  4. Dataset (codesentinel/rig/dataset.py): a before-fix candidate judged flaw_visible with lines becomes a flawed sample; an after-fix candidate judged no_flaw becomes a flaw-free sample; everything else is excluded and logged. --pairs-only keeps a pair only when both halves are included. kappa reports Cohen's kappa between two reviewers.

The current candidate set is 204 pairs from 113 repositories.

11. Running on a cluster

study/hpc/run_array.sbatch is a Slurm array job. Each task requests one GPU, starts a vLLM server for the model on a task-specific port, waits for /v1/models, then runs python -m codesentinel.rig run --backend openai --shard i/n. Shards write separate files, so tasks do not contend and a failed task can be resubmitted alone.

Reproducibility captured per task: GPU model, pip freeze, the server's /v1/models response. Record the model's weight revision as well.

The script has not been executed on a cluster yet. study/hpc/README.md has the setup and a four-sample smoke test to run first.

12. Extending the system

Add a detection rule. Append a Rule(...) to RULES in codesentinel/rules.py, cite an existing passage id in rag/data/patterns.md or add one, and add a positive and a negative case to the tests. Remember that the first matching rule wins per line, so order matters.

Add a model backend. Write a class with a model attribute and call(system, user, max_tokens, temperature, seed) -> (text, usage_dict), where usage_dict has input_tokens, output_tokens and served_model. Register it in runner.make_inner and in the CLI's --backend choices.

Add a configuration. Add a branch to arms.run_arm, add the name to ARMS and to runner.ORDER. If it patches the scanner, do it inside _patched so the patch is undone. Add a comparison pair in analyze.analyze if it should be compared by default.

Change the scoring rule. Do not change score_legacy. Change score or TOLERANCE only before a pre-registration commit; the rule name and tolerance are written into every provenance statement.

Sign statements. Wrap attest's output in a signature over attestation_head.json. The chain design needs no change.

Not covered by tests: any behaviour against a real model, the Slurm script, and the candidate builder's network path.

14. Security considerations

  • Scanned code is untrusted input to a model. Text in comments can attempt to instruct the reviewer. The planned adversarial set measures this; nothing in the pipeline prevents it today.
  • AI review sends code to the model provider. Use the rule engine or a self-hosted model where that is not acceptable.
  • Record files contain the scanned code and model output in clear text. Treat a run directory with the same sensitivity as the code.
  • The label tool binds to 127.0.0.1 and has no authentication. Do not expose its port.
  • The candidate builder runs git fetch against third-party repositories. It executes no fetched code and parses Python with ast only.
  • Candidate samples are real vulnerable code from public fixes, redistributed for evaluation under each project's own licence. Check the licences before publishing a dataset built from them.
  • The retrieval index is a pickle. Load only an index you built with codesentinel ingest.

5. Where CodeSentinel can stand

It cannot win on rule coverage, analysis depth or distribution. Three things are different:

  1. Finding-level provenance. Each result carries a hash-chained statement of the model responses, prompts, retrieved passages and code version behind it, and a verify command re-derives the findings from recordings.
  2. An open evaluation rig. A buyer can run a single prompt, an equal-call control, the full pipeline and its ablations on their own code and get paired statistics with intervals. This is a tool for deciding whether any AI reviewer earns its cost, not only CodeSentinel.
  3. Stated limits. The repository publishes what its own pilot does and does not show.

I did not find a mainstream scanner that publishes replayable per-finding provenance of this kind, but I have not surveyed the field exhaustively. Treat "unique" as a hypothesis to check with buyers, not a fact.
